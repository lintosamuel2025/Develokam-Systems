IT Hardware & Support Fundamentals

Before troubleshooting a network or a server, you need to be comfortable inside a machine and confident on a support call. This course covers computer hardware from the component level up, then moves into the diagnostic habits and ticketing discipline that first-line and desktop support roles are actually judged on.

Duration
4 weeks · 3 sessions/week
Level
Beginner
Who it's for
Absolute beginners, career switchers and anyone preparing for a first IT support or helpdesk role.
Prerequisites
None — basic computer literacy is enough to start.

Learning objectives

  • Identify, install and troubleshoot core PC hardware components
  • Build and image a Windows desktop from scratch
  • Run a structured first-line support call, including triage and escalation
  • Log, update and close tickets to a standard a supervisor would accept

Syllabus

Computer Hardware Fundamentals
  • Motherboards, CPUs, RAM and storage
  • Power supplies and cooling
  • Peripherals and ports
  • Diagnosing hardware failures
  • Assembling and upgrading a desktop
IT Support Fundamentals
  • The support ticket lifecycle
  • Triage and prioritisation
  • Remote support tools
  • Escalation paths and SLAs
  • Communicating with non-technical users
Desktop & Technical Support
  • Windows installation and imaging
  • Driver and peripheral setup
  • Common desktop faults
  • Printer and peripheral troubleshooting
  • Asset tagging and handover

Practical labs

  • Build a working PC from individual components
  • Image and provision a desktop end to end
  • Run a mock support call from ticket to resolution

Projects

  • Diagnose and document a set of seeded hardware faults
  • Produce a first-line support runbook for a small office

Tools & technologies

Windows 11 Ticketing software (Freshdesk/Zoho Desk style) Basic diagnostic utilities

Certification

Prepares you for entry-level vendor certifications such as CompTIA A+ (exam not included).

Career opportunities

IT Support Technician Desktop Support Engineer Helpdesk Analyst

Frequently asked questions

Do I need any prior IT knowledge?

No — this is the starting point for the whole academy.

Is this course hands-on?

Yes. You will build, image and troubleshoot real hardware and run mock support tickets.

8 weeks · 3 sessions/week
Level
Beginner → Intermediate

Learning objectives

  • Configure and troubleshoot VLANs, trunking and STP
  • Configure static routing, OSPF, DHCP, NAT and ACLs
  • Secure and troubleshoot a small-to-medium enterprise network
  • Sit the CCNA exam with confidence, backed by lab experience

  • Wireless networking

Troubleshooting

  • Cisco Packet Tracer scenario labs

Practical labs

  • Multi-router OSPF topology
  • NAT and ACL configuration on a simulated edge router
  • Wireless LAN configuration
  • Timed troubleshooting scenarios on Packet Tracer

Projects

What is DNS?

Every time a browser, an app or a server needs to reach another machine by name, DNS is the step that turns that name into an IP address. It is one of the oldest parts of the internet's plumbing, and one of the first things a support engineer should suspect when 'the internet is down' actually means 'one thing is down.'

A DNS record maps a name to a value — most commonly an A record mapping a hostname to an IPv4 address, but also MX records for mail, CNAME records that point one name at another, and TXT records used for verification and anti-spoofing policies like SPF and DKIM.

Resolution happens in stages: a resolver checks its cache, then asks a recursive resolver, which walks from root servers down through top-level domain servers to the authoritative server for that specific domain. Caching at every stage is what makes DNS fast — and what makes a changed record take time to propagate everywhere.

For anyone starting in networking or IT support, the practical skill is diagnostic: knowing how to query a record directly, tell a caching problem from a misconfigured record, and read a zone file without panicking. That diagnostic habit is exactly what our Networking Fundamentals & Troubleshooting course builds from week one.

DHCP Explained for Beginners

DHCP — Dynamic Host Configuration Protocol — is the reason you can plug a laptop into almost any network and get online without manually configuring an IP address. A DHCP server hands out addresses from a defined scope, along with the subnet mask, default gateway and DNS servers a device needs.

The process is a four-step conversation, often remembered as DORA: Discover, Offer, Request, Acknowledge. The client broadcasts a discovery request, a server offers an address, the client requests that specific offer, and the server acknowledges it — at which point the address is leased, not owned, for a defined period.

Leases matter because addresses are finite and devices come and go. A short lease time suits a busy guest network; a longer one suits a stable office LAN with static reservations layered in for printers and servers that need a predictable address.

Troubleshooting DHCP is a rite of passage in IT support: a device with no address at all almost always means it timed out waiting for an offer, while duplicate-address conflicts point to overlapping scopes or a rogue DHCP server on the network. Both are covered as hands-on labs in our Networking Fundamentals & Troubleshooting course.

How Active Directory Works

Active Directory (AD) is Microsoft's directory service for Windows domain networks — a central database of users, computers, groups and the permissions that tie them together. If you've ever logged into a work computer with a company account, AD (or something built on the same ideas) was almost certainly behind it.

The core structure is a domain, organised into Organisational Units (OUs) that group users and computers for management purposes. Group Policy Objects (GPOs) attach settings and restrictions to those OUs, which is how an organisation can enforce a password policy or lock down a desktop setting across thousands of machines at once.

Authentication in a modern AD environment typically runs on Kerberos, a ticket-based system that avoids sending passwords across the network repeatedly. Understanding that flow — and the DNS dependency AD has, since domain controllers rely on it to find each other — is what separates someone who can click through AD Users and Computers from someone who can actually administer a domain.

Our Windows Server Administration & Active Directory course builds this from a bare server install: promoting a domain controller, structuring OUs, delegating permissions properly, and applying Group Policy the way a real environment needs it.

CCNA Roadmap for Beginners

CCNA has a reputation for being where networking beginners get stuck, usually because they start with the certification instead of the fundamentals underneath it. The fix is sequencing: build comfort with IP addressing and subnetting before touching VLANs, and understand VLANs before layering routing protocols on top.

A realistic roadmap looks like this: start with core networking fundamentals (OSI/TCP-IP models, IPv4 addressing, cabling and media), then move to switching concepts (VLANs, trunking, STP), then routing (static routes, OSPF), and only then the services and security topics — DHCP, NAT, ACLs, wireless and network security basics — that round out the current CCNA syllabus.

Lab time matters more than video time. Cisco Packet Tracer is free and lets you build the exact topologies CCNA tests you on, which is why every module in our CCNA course pairs directly with a lab rather than sitting behind a wall of slides.

Once the syllabus feels familiar rather than intimidating, the exam itself becomes a formality — a checkpoint on skills you already have, not a hurdle you're hoping to clear.

Linux

Linux Commands Every IT Engineer Should Know

You don't need to memorise every Linux command to be productive — you need a working set that covers navigation, inspection and troubleshooting, and the confidence to look up the rest.

For navigation and files: ls, cd, cp, mv, rm, and find for locating files by name or type. For inspecting what's happening on a system: ps and top for processes, df and du for disk usage, and tail -f for watching a log file update in real time.

For permissions and users: chmod and chown, plus sudo for privileged commands — understanding the difference between a permission problem and an ownership problem saves hours of confused troubleshooting.

For networking from the shell: ip a (or the older ifconfig) to check addressing, ping and traceroute for connectivity, and ss or netstat to see what's actually listening on a port. These are exactly the commands used throughout our Linux System Administration course, applied to real Ubuntu and Red Hat servers rather than memorised in isolation.

DevOps

What is DevOps?

DevOps gets described as a toolset — Git, Docker, Jenkins, Kubernetes — but the tools are downstream of an idea: that building and running software work better when the same team (or at least the same workflow) owns both, with everything versioned and as much as possible automated.

In practice that means: code and configuration live in version control (Git), not on someone's laptop. Applications are packaged consistently (Docker) so 'it works on my machine' stops being an excuse. Deployment is automated through a pipeline (CI/CD, via tools like Jenkins or GitHub Actions) rather than a manual checklist. And infrastructure itself is defined as code, so an environment can be rebuilt exactly, not just remembered.

None of this requires all the tools at once. A small team's first real DevOps step is usually just consistent Git branching and a single automated build step — the container orchestration and infrastructure-as-code layers come once that foundation is solid.

Our DevOps Engineering course follows that same order deliberately: Git and Linux fundamentals first, then containers, then a full CI/CD pipeline, so the workflow makes sense before the tool list gets long.

Git vs GitHub

Git is version control software that runs locally: it tracks changes to files over time, lets you branch to work on something without disturbing the main codebase, and lets you merge that work back in. You can use Git entirely offline, on a single machine, with no internet connection at all.

GitHub is a hosting service built around Git — a place to push your repositories so others (or your future self, from another machine) can access them, plus collaboration features Git itself doesn't provide: pull requests, code review, issue tracking, and GitHub Actions for automation.

The confusion usually comes from how often the two are used together: git push sends your local commits to a GitHub repository, and that combination is so common that 'Git' and 'GitHub' get used interchangeably in casual conversation. They aren't the same thing, and knowing the difference matters the first time you need to explain why a local commit isn't visible to a teammate yet — it simply hasn't been pushed.

Both are covered from first principles in our Programming Fundamentals with Python and DevOps Engineering courses, since almost every track past the basics assumes comfort with both.

How to Become a Network Engineer

The honest path into network engineering runs through fundamentals most people are tempted to skip: comfortable IP addressing and subnetting, a working mental model of how switches and routers actually forward traffic, and enough hands-on lab time that a topology diagram doesn't feel abstract.

From there, CCNA is the standard, recognised checkpoint — not because the certificate itself does the work, but because studying for it properly forces you through VLANs, routing protocols, NAT, ACLs and basic security in a structured order.

Entry-level roles — NOC analyst, network support technician, junior network administrator — are usually the realistic first step, giving you exposure to real tickets and real hardware before a pure network engineer title. CCNP Enterprise and specialisation (security, wireless, automation) tend to come after a year or more of that hands-on exposure.

We don't promise a job at the end of any course — the market and your own effort decide that — but the sequence above (Networking Fundamentals & Troubleshooting → CCNA → entry-level role → CCNP Enterprise) is the one our own trainers followed themselves.

Entry-level IT support interviews rarely ask trick questions — they ask you to narrate how you'd think through a problem, because that's what the job actually is. Expect: 'Walk me through what you'd check if a user says their internet isn't working,' or 'How do you prioritise five open tickets at once?'

Technical questions tend to be practical rather than theoretical: explaining the difference between a switch and a router in your own words, describing what happens when a device can't get an IP address, or what you'd check first if a printer won't print.

The strongest answers are structured, not memorised — start broad (is it just this user, or everyone?), narrow down systematically, and say out loud what you'd check and why. Interviewers are listening for method as much as the correct answer.

Behavioural questions matter more than beginners expect: describing a time you had to explain something technical to a frustrated, non-technical person is one of the most common questions in first-line support interviews, precisely because the technical skills are teachable and the communication habit is harder to fake.

How to Become a System Administrator

System administration usually starts on whichever platform your first job runs — but the underlying skills (users and permissions, services, patching, backup and monitoring) transfer directly between Windows Server and Linux, which is why most working sysadmins end up comfortable with both.

A common, sensible order: build IT support fundamentals first, then Windows Server and Active Directory (still the backbone of most corporate networks), then Linux administration, since a growing share of servers, containers and cloud instances run on it.

From there, virtualisation and backup/recovery round out the core skill set — most environments run multiple servers as virtual machines, and 'have you actually tested a restore, not just configured a backup' is one of the most telling interview questions in the field.

Cloud administration (Azure or AWS) is the natural next step once on-premises fundamentals are solid, which is exactly the order our own System Administration and Cloud Computing courses follow.

DevOps

Docker Explained for Beginners

Docker packages an application together with everything it needs to run — code, runtime, libraries, configuration — into a single container image. That container runs the same way on a developer's laptop, a test server and production, which eliminates the classic 'it works on my machine' problem.

A container is not a virtual machine: it shares the host operating system's kernel rather than virtualising an entire OS, which is why containers start in seconds and use a fraction of the resources a VM does.

The core workflow is simple: write a Dockerfile describing how to build the image, build it, and run it as a container — optionally pushing the image to a registry so it can be pulled and run anywhere else. Once you're running more than a handful of containers, orchestration tools like Kubernetes take over managing them at scale.

Our DevOps Engineering course teaches Docker exactly in that order — building and running single containers first, before Kubernetes enters the picture.

Azure

Azure Fundamentals Roadmap

Azure has a huge service catalogue, which makes 'where do I start' a genuinely hard question. The honest answer: start with the resource model (subscriptions, resource groups, regions) and identity (Microsoft Entra ID), because almost every other service depends on how access is structured.

From identity, networking is next — virtual networks, subnets and network security groups are the backbone that storage accounts and virtual machines sit inside. Trying to learn VMs before networking usually means re-learning networking concepts under pressure later.

Storage and compute (storage accounts and virtual machines) come after that, followed by backup and disaster recovery — often the most skipped topic, and the one that matters most the first time something goes wrong.

This is precisely the order our Microsoft Azure Administrator course follows: fundamentals and identity, then networking and storage, then virtual machines, then backup and disaster recovery, each with a hands-on lab.
